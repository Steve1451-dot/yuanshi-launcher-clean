# 0.2.83：集中整合候选版与自动日志轮换

## 本轮要求

用户要求把已有优化集中整合，减少需要用户反复测试的安装包，并且一开游戏就
自动后台记录，达到容量上限后清理更早日志。本轮只交一个候选包，不要求再测
多个分支或手动写标记。不将未验收的实机硬解、声音和流畅度称为完全完成。

保留 0.2.82 的实验硬解优先、初始化/首帧失败回退、异常退出保护、软件选择、
低开销颜色显示、有界 GPU 槽位扫描，以及 0.2.80/81 的收包恢复与显示时钟。
原神与终末地共享本轮媒体/日志改动，已有登录和码率/帧率配置不变。

## 自动记录和清理的精确范围

- 默认自动记录，不用手动导出；启动、登录、排队、串流和异常都有安全事件。
- 历史目录：AppHomePath()/stream-logs，默认 SD 路径为
  sdmc:/switch/SwitchNOW/stream-logs/。
- 仅管理固定名称 stream-safe-00.log 到 stream-safe-15.log。
  单段最大 512 KiB，16 段共最多 8 MiB 的受管历史。
- 当前段写满后选择空槽；没有空槽时按时间淘汰最早的有效日志。时间相同或
  SD 后端不能提供时间时，用轮转顺序处理，避免反复只覆盖一个槽。
- 跨应用重启保留旧段；同次运行增量追加，不在每次保存时复制整份长历史。
  日志按应用运行时间和事件序号区分，STREAM_ENTRY 等事件标出新的游戏串流。
- 每次写入只使用 SafeEventLog 验证过的事件名与数值，不保存账号、Cookie、
  令牌、二维码、地址、SDP 或视频帧。轮换旧日志会覆盖旧记录，不能恢复。
- 不枚举或递归删除任意目录。不跟随日志目录/文件符号链接；固定槽位内的
  陌生内容、截断文件或异常大文件会留在原地并跳过，而不是删除或阻止其余槽。
  因而用户放入的非受管内容不属于这 8 MiB 预算，也绝不会被用来自动清空间。
- 原兼容文件 cloudgenshin-safe.log 继续保存最新英文快照，另计，限制为 128 KiB，
  保留启动证据和最近事件，省略的中段有计数。手动导出的中文快照也仍保留。
  8 MiB 指受管历史，不是整个 SwitchNOW 目录、其他日志或登录文件的总容量。

写盘仍由已有独立后台线程执行，多个请求合并成一个待写标志，约 2 秒内不反复
刷卡；媒体计数仍约每 5 秒汇总，不逐包/逐帧写盘。退出会尽力刷完待写内容。
突然断电/进程崩溃仍可能丢失最后一批尚未刷出的事件，不宣称日志绝不会丢。
移除了线程创建失败时在 RTC/UI 线程同步写卡的兜底：此时保留内存日志并记录
明确状态，手动导出仍可用，避免用写盘停顿破坏游戏。未加新日志线程。

最新快照的 128 KiB 字节上限也修复了“新增诊断导致文件超过监测器读入上限，
结果整份快照被拒绝”的问题；RAM 历史仍有事件数上限，磁盘历史另走增量轮换。

## CPU 和内存开销

新增压缩视频包缓存池，在已有队列锁下复用存储。最多 8 个缓存、总保留量
2 MiB，单个大于 512 KiB 的 IDR 缓存不长期保留。队列仍受原来的长度与 67 ms
积压规则限制，未通过无限加缓存换取表面流畅。

回收覆盖正常解码、旧代结果、积压清理、重新同步、首帧失败回退及停止。停止
清空缓存；低内存分配失败转入等待关键帧恢复，不把异常抛出到网络线程。
输入直接 assign 到复用存储，不先清零再整包覆盖。FFmpeg 仍保留原安全 padding
和持有时长策略，这不是压缩数据端到端零拷贝，也没有改变 GPU 表面的所有权。

没有凭推测绑定 CPU 核心或增加系统超频：核查 [libnx 的线程创建实现](https://github.com/switchbrew/libnx/blob/master/nx/source/runtime/newlib.c)
后，没有发现 std::thread 被该运行时统一限制在单核的依据。已有后台日志线程
也不重复创建。没有从截图把卡顿认定为内存容量不足。

## 更有用的分阶段数据

- 解码调用超过 16.7 / 33.3 ms 的近期次数与近期最大值，区分低平均值掩盖的
  长停顿。它们是 API 调用的墙钟分布，不是精确每帧 CPU 利用率或 P95。
- UI 分为输入处理、取帧/提交、后续面板绘制三段，另记两次 draw 之间外部
  间隔峰值。外部可能包含交换链等待、框架任务和调度，不当成纯 GPU 时间。
- 缓存新分配/复用/失败次数以及当前保留字节数，验证缓存优化是否实际生效。
- 所有新增标量有中文解释并加入安全监测白名单。每秒计算近期窗口，仍每约
  5 秒汇报最近窗口；历史峰值和累计计数保留，不伪造连续每秒的完整性能追踪。

这些指标不改变收包、解码、提交 FPS 的真实计数，不隐藏仍存在的丢弃或卡顿。
软件/硬解选择仍在下次会话生效，未加入不安全的后台 GPU 表面热切换。

## 集中验证

缓存单元测试：10000 次复用保持同一分配，验证数量/字节上限与大缓冲排除。
生产 MediaPipeline/恢复/缓存/CV 生命周期模型：200 个模拟 RTP 视频包，
1 次缓存分配、199 次复用；覆盖积压、等待 IDR、首帧硬解错误回退、20 次启动停止。
该模型以确定性解码/音频替身运行，不等同于真正 H.264、NVDEC 或音频设备测试。

日志测试覆盖跨运行保留、缩小额度下的 16 段轮换、去重、凭据夹具不动、陌生
槽位不覆盖、符号链接拒绝（操作系统允许建立链接时）、高频后台请求合并、
失败后继续记录、128 KiB 超长事件快照的启动/最近证据保留。

本轮没有新的 yuzu、真实账号排队或物理 Switch 游戏运行。不用模型测试和构建
结果承诺稳定 60 FPS、硬解黑图根治或所有重连均已验收；这一候选包集中保留
已有修复和新数据，供一次有针对性的实机验收，避免用户反复切换零散版本。

最终 35 项主机用例、2 项生产渲染器模型、3 项安全监测测试、8 项 DTLS/UDP/RTP
CTest 通过。完整 devkitA64 NRO 构建与内嵌 0.2.83 版本校验通过。匹配 ELF 与
NRO 冻结到工作区 outputs/consolidated-candidate-20261027；公开包不含运行数据。
