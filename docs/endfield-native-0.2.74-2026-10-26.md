# 终末地原生适配 0.2.74：启动顺序与退出链路

日期：2026-10-26（Asia/Singapore）。延续 0.2.73，没有重新扫码、购买时长、接受协议或使用桌面 UI 自动化。协议修复未修改原神通路；随后核对并编入了协作者较新的公共手柄采样、来源交接和发送失败重试实现，未覆盖其修改。已保存登录的格式没有变化。

## 已落实的协议事实与修复

1. APK `CloudServerErrorCode.SESSION_NOT_QUEUING=23001`。`CloudApiPath` 把 `/api/v1/session/cancel` 定义为 CANCEL_QUEUE，不能把其结果当作游戏停止接口。删除了拿 game_session_id 再试一次的猜测逻辑；安全事件改为 QUEUE_CANCELLED / QUEUE_NOT_ACTIVE / QUEUE_CANCEL_FAILED，明确区分“已不在排队”和“云端游戏已结束”。0.2.73 笔记中关于 23001 的诊断以此为准。
2. 官方网页 SDK 模块 6868 的 `onFirstVideoFrame -> FIRST_VIDEO_FRAME_RECEIVED(6038)` 先调用 R4 开启 app interception，再通知 gameManager；模块 6718 的 6038 回调才发送 PipelineConnected。PipeState 是另一类回调 6252。旧实现把 APK 的 PipeState 时机与 WebRtc 的消息方言混在一起，且在 intercept_app 前通知初始化。
3. 新的 `PostFramePolicy` 要求真实解码首帧与本地 intercept 写入均完成，才让 WebRtc 桥发送一次 PipelineConnected。FPS 与 intercept 各有独立的 20 次 / 500 ms 重试预算；先处理 intercept，避免 FPS 重试耗尽 SDK 通路的机会。这里只确认本地写入，不声称服务器已应用设置。
4. `VlinkSession::stop` 不再写入退出包后立即销毁 SCTP。只在网络工作线程中做有界的本地发送重试与排空：拒绝写入最多重试 250 ms，接受后处理连接约 500 ms，总防御期限 750 ms（单次受限网络调用和调度仍有少量超出）。停止时不再向业务桥、解码或 UI 转发收到的数据。退出本地入队和云端结束确认是不同事实，日志不伪造后一项。
5. 接入 SCTP open/close 回调。业务控制连接关闭时，不再凭持续 RTP/片头画面假装能继续操作；停止本次会话并给中文原因。增加每 5 秒的本地控制消息发送/失败/收到计数，没有逐包落盘，也不输出包体。
6. `SubmitGameData` 只记录 APK 固定的 1..11 类型枚举；未知值统一为本地 -1。7 是 app 启动，8 才是账号登录，3 才是角色进入，6 是清除角色状态。uid、roleId、自定义事件及请求正文不进入诊断。generic GameData 不能被提升为角色进入。

以上实现未改 `extern/`。已有脏工作区和其他修改均保留，未提交、推送或创建定时任务。

## 复测方法与安全边界

`scripts/endfield-control-close.gdb` 只用于匹配 ELF/NRO 的 yuzu EA4176，代码基址 0x80000000、回环调试端口 6543。两个函数入口处 x0 用法已离线核对；只读连接标志、收包计数、队列长度和接收失败标志，不读凭据/正文，不调用被调试进程里的函数。更换二进制或模拟器后须重新核对，不能照搬地址和假设。

`scripts/start-cloudgenshin-autotest.ps1` 用有界白名单记录上述标量。报告的 HarnessDeadlineReached 表示主动测试截止，不是游玩成功；Failed=false 也不是项目已完成。测试标记只能放在独立 SD，测试后移入本轮报告归档，不装进发布包，不让后台继续排队。

## 后续确认的 SDK 重试缺口（独立于前述手柄冻结包）

旧包对照 `outputs/controller-check-20261026/prior-binary-control-run` 也在 158 秒主动截止前停留启动动画，解码 4086、错误 0、业务消息 31。因此不能把间歇启动停滞直接归因于新的手柄代码。

在 GameBridge 找到可确定重现的恢复缺陷：Pending 回包的 15 秒发送预算耗尽后，会删除回包，但 handled 去重名单仍保留请求身份；远端重发同一个 SDK 请求被当作已完成，不再获得回复。另一个缺口是 32 项近期名单被普通通知刷出后，仍在等待发送/授权的请求失去去重保护。

修复让 Pending 携带仅存于内存的来源身份；过期未确认时移除相应近期去重，允许远端重发恢复；仍在途的回复和异步登录刷新独立阻止重复。确认过的请求维持原有近期去重；过期登录请求重新取授权码，不复用丢弃回包中的旧码。16 项发送队列、15 秒单次预算和回调格式不变，没有加入自动重新排队、购买、假协议确认或自动循环登录。

新增测试在修复前于 `retry.receive(query,15000)` 确定失败；修复后完整 GameBridge 测试通过。覆盖 AndroidSdk/WebRtc 两种方言、15 秒边界、旧 ACK 不得删除新回包、确认后抑制重复、登录重新刷新授权，以及 40 条普通通知后仍在途请求的去重。

还复现并修正了接收与定时器的先后边界：网络线程先排空收到的消息，再调用 poll；截止时收到的重发不能命中一个马上会被 poll 丢弃的旧 Pending。收到业务请求前先过期整理，迟到 ACK 仍优先确认尚未丢弃的回包。全部本地发送被拒绝、没有先调用 poll 的 15 秒边界测试也通过。

首个恢复修复候选 D02ECC... 的 `sdk-retry-run` 在 41 秒附近发生真实控制通道关闭，最终安全日志为 NroTestFailed，视频解码 35、业务消息 27。此结果明确不支持“修完重试就已经可玩”的说法；SDK 重试恢复与底层通道关闭须分别处理。该候选的后续只读关闭原因检查不使用周期/逐包断点，仅在关闭发生时读取固定的失败标志，避免在传输中暂停。

这修复了一个真实恢复缺口，不等于已证明它是所有启动停滞的唯一原因。前述 69676... 冻结 NRO 和安装包仍是修复前的手柄验证副本；后续 SDK 重试候选必须使用独立文件名与哈希，不得混用测试结果。
