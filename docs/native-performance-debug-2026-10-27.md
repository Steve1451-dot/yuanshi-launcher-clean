# 0.2.82：实验硬解优先、低开销显示与可归因诊断

## 截图能证明什么

用户截图：720p 软件解码、2.75 Mbps，近期完整接收 / 解码 / 新帧提交为
41 / 36 / 17 FPS；显示队列跳过 20 帧，等待关键帧丢弃 4，解码拥塞丢弃 0。
这支持优先检查本机解码到显示的交付损失，不支持直接断言热点带宽不足。
码率不是测速结果，不能由 2.75 Mbps 排除网络抖动，也不能把 20 次显示跳过
当成无线丢包。36→17 不能只用“软件解码慢”解释。

14.38 ms 是近期每次解码提交/接收调用的平均墙钟耗时，可能一次输出多帧或
暂不输出；不是精确单帧 CPU 使用率。0.34 ms 只是渲染提交调用的 CPU 耗时，
没有覆盖整个 UI 循环、取得交换链图像或 GPU 完成时间，不能据此排除显示瓶颈。
366.4 ms 是会话最大轮询间隔，可能发生在此前阶段，不能当作当前 RTT。

CPU 软解、内存帧搬运和显示调度都值得优化；截图没有内存容量耗尽证据。
硬解将 H.264 工作交给 NVDEC，既有 Deko3D 硬件表面映射避免正常播放逐帧下载；
不等于消除所有 CPU 工作、所有内存访问或网络问题。

## 行为变化（两处原生视图统一）

1. 新默认优先尝试实验 NVDEC，不再需要手写 probe 文件。仍使用已有 H.264
   hwaccel 能力查询、硬件格式选择、帧率和 RTP 时间基，不修改认证或传输协议。
2. 初始化失败会退软解；首次输出之前的解码错误允许一次软件重建并等待 IDR。
   已向 UI 发布硬件帧后，不从后台强制重建解码器，不提前释放 GPU 持有表面。
   尚未实现任意阶段错误的自动热切换；不能称为无缝恢复已验收。
3. 硬解前在 AppHomePath 写入 cloudgenshin-nvdec-active.txt。正常退出并停止
   渲染/媒体后删除；异常退出残留或保护文件不可写时，下次安全使用软件。
   保护命中不等于证明上次崩溃一定由硬解造成，也可能是强制关机等原因。
4. 两边触摸悬浮球的菜单新增“下次解码方式（实验）”，在优先硬解和软解间切换。
   选项原子保存到 cloudgenshin-decoder.txt，重进串流才生效，不强制切换正在
   使用的 GPU 表面。选软解再选硬解可显式重试残留的硬解保护；异常路径不自动
   无限重试。黑屏时可用覆盖在游戏画面上的菜单选软解，停止后重新开始。
5. 原生 Deko3D 播放关闭可选的多采样去噪/锐化，仅保留必要颜色转换。只改当前
   原生渲染器的选项，不覆盖用户通用画质设置，也不修改 GFN 默认增强策略。
6. 上传槽和更新命令槽进行固定容量、非阻塞扫描，不因单个游标位置忙就放弃
   其他空闲槽；全部忙仍复用旧帧。准确给实际使用的命令片段记录完成 fence。
   不增加槽位、取消同步或在正常播放调用 waitIdle。

注意：此前 yuzu 的硬解曾输出黑图，尚未确定是模拟器还是设备后端问题。
本版是明确的实验硬解优先版本，不冒充已通过 Switch 画面/流畅度验收。
硬件格式帧计数增长、初始化成功或 GPU 命令提交都不是正确像素证明。

## 每次反馈能带回的诊断

性能 HUD 仍显示近期完整接收、解码、新帧提交、解码/排队/渲染 CPU、IDR 恢复、
显示跳帧及音频信息；新增：

- UI 实际 draw 回调频率与近期最长间隔（不是物理显示 FPS）。
- 全部命令槽忙、全部上传槽忙、硬件帧引用受阻、硬件表面映射失败，分别计数。
- 近期轮询最长间隔与会话历史峰值分列，不再将历史峰值当成本秒停顿。
- 样本编号、区间长度、近期真实硬件格式输出帧数。

UI 每约 1 秒更新窗口；现有每 5 秒安全日志快照记录最近一个完整窗口，FPS
用 MILLIFPS 整数保存（17000=17 FPS），间隔用微秒。样本编号可识别重复旧窗口。
网络线程只读取原子标量镜像；用有界的两次版本检查保证一个报告不混入两次
UI 更新，冲突则记录 SNAPSHOT_BUSY 后略过，不无界自旋或阻塞绘制。

日志不保存每个 1 秒窗口，因此也保留 UI 历史峰值和 GPU 各原因累计数，避免
短暂问题恰好不在第 5 秒就完全丢失证据。短暂峰值发生的准确时刻仍非完整追踪。
新增指标全部有中文解释和源定义安全白名单，没有每包/每帧写 SD、GPU 强制下载、
账号、Cookie、地址、SDP 或二维码内容。

判读优先级：

| 同期现象 | 进一步检查方向（不是单项因果证明） |
| --- | --- |
| 软解、解码慢且解码排队/拥塞增长 | CPU 解码和调度压力，检查硬解是否回退及原始错误码 |
| 解码足够但 UI draw 很低 | 主循环、交换链/GPU、UI 工作与 CPU 调度；小的渲染 CPU 不足以排除这些 |
| UI 足够但 GPU 暂缓计数增长 | 根据命令、上传、引用、映射分类检查同步/资源压力 |
| 近期轮询停顿且 RTP/IDR 恢复增长 | 本机收包线程阻塞/调度及外部网络都需区分 |
| 硬解帧增长但黑图/花图 | 硬件像素正确性尚未通过，不能把计数当成性能成功 |

## 验证

28 项相关主机用例通过：新增选项/异常保护/严格配置读取、槽位扫描、有界同步
诊断镜像、近期与历史峰值分离，并回归显示时钟、引用生命周期、输入、SDK、
音频与恢复策略。3 项安全日志监测测试通过；8 项 DTLS/UDP/RTP/H264 CTest 通过。

生产 Deko3D 实现的两个模型回归通过：分辨率/后端切换、26/11 个资源分配失败
位置、fence 生命周期、软件上传全部忙与硬件命令全部忙的正确计数、实际提交
generation、颜色范围以及低开销参数。模型使用真实 FFmpeg 头和确定性引用/GPU
替身，不是 FFmpeg 解码、物理 NVDEC 或真实 GPU 测试；原真实主机链接入口保留。

本轮没有启动新的 yuzu/实机运行，没有使用账号文件。模拟器不黑屏可作为功能
回归证据，但不能还原 Switch 的 CPU、内存带宽、NVDEC、Wi-Fi、散热/电源条件。
不以旧版硬解帧数或旧版游戏截图冒充本版的运行结果，不承诺已达稳定 60 FPS。

硬解选择、低开销显示和安全诊断镜像实现。NRO 与匹配 ELF 仅在工作区
