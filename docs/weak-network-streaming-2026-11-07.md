# ys / zmd 弱网流畅保护

两种协议共用 `mihoyo/adaptive_stream_policy.hpp`，替代先前仅 zmd 使用的
`endfield/adaptive_bitrate.hpp`。仍使用现有、已验证的码率与帧率命令，
不修改依赖库、输入格式、RTP 修复窗口、解码器回退或有界队列。

## 决策

- 网络线程每秒读取一次累计 RTP 统计，策略以不少于 2 秒的窗口判断。
- 连续两个窗口存在明显未修复画面损坏时，码率上限降低 25%；严重损坏
  可在一个窗口后降低 50%。成功完成一次设置后至少等待 8 秒再调整。
- 所有画质档位均可临时降低至 3000 kbps 下限。手动选择的画质代表恢复
  上限；高画质 / 省流 / 极省流的正常范围仍为 6000–12000、4000–8000、
  3000–4000 kbps。最低请求码率不会低于 3000 kbps。
- 到达最低码率后仍有持续损坏，临时请求 30 FPS。连续解码队列溢出也可
  触发降帧，此时不会仅因本地负载而降低码率。
- 连续干净且有实际画面流量约 45 秒，先恢复用户选择的 60 FPS；之后再
  每积累约 30 秒干净流量，以约 10%（至少 250 kbps）逐步恢复码率。
- 用户选择的 30 FPS 不会自动升至 60。自动设置仅作用于当前会话，不写入
  保存的偏好。手动设置、控制通道恢复、统计重置和采样中断会取消旧自动请求。
- 每次调整沿用设置下发预算：间隔至少 500 ms，3 次成功本地写入后停止，
  最多尝试 20 次。不会逐包或逐帧发送控制命令。

实际判断使用 RTP access unit 损坏、重排超时 / 容量丢弃，以及解码队列
溢出计数。已修复重传、显示跳帧、静止画面的低实际码率和单纯高 ping
不会被当成带宽不足。无流量、时间回退、统计重置或长时间采样中断不能
被算作网络恢复。控制统计采样不依赖诊断日志是否开启。

## 界面和边界

悬浮窗在临时降低设置时显示“流畅保护中”，自动降帧时显示
“自动调整：30 帧”。顶部 FPS / Mbps 继续显示实际接收解码统计；菜单
保留用户设置。设置写入成功表示本地传输接受，并不表示收到服务端 ACK。

3 Mbps 是客户端请求下限，服务端仍可能根据场景或策略发送更少数据。
链路无法承载该下限时仍可能卡顿；本改动不承诺低于此带宽仍能流畅游玩。
完整登录、移动镜头、无线干扰和恢复效果需要 Switch 实机验证。

## 验证

- `adaptive_stream_test.cpp`：持续 / 严重损坏、低码率降帧、恢复顺序、
  所有档位边界、30 FPS 手动上限、解码拥塞、无流量、计数 / 时钟重置、
  中断、取消、失败和部分成功的有界重试。
- 生产 `rtc::Session` 离线传输测试验证动态范围命令与单位，以及无认证和
  越界请求不发送数据。
- 双语悬浮窗绘制测试、设置 / 保存兼容，以及解码队列、恢复、显示队列和
  时钟相关主机测试。
- 使用 `build-switch.ps1` 完成完整 Switch NRO 构建；版本仍为 0.2.111。
