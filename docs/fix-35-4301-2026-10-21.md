# 35-4301 专项排错（2026-10-21）

状态：**已修复并在实机进入游戏场景验证**（0.2.46，2026-10-21 19:27–19:30）。

唯一验收目标：真实云原神在点击进入后不再出现 35-4301，观察到游戏加载/进入
证据。收到视频、成功排队、NRO 构建通过、SDK 本地回 true/ret=0 都不算目标完成。

## 根因

同一份旧存档、同一真实账号令牌，只补官方账号类型 `account_type=1` 后不再弹
35-4301，并首次出现“准备进入游戏”事件；不补则稳定复现。旧 vault（264 B）
保存了已验证的官方渠道身份和 Combo 令牌，但没有 SDK 账号命名空间中的
`account_type`。原神国服官方账号 SDK 将米哈游账号标为类型 1；服务端在进入
游戏前的账号校验中拒绝缺少该类型的登录回包。

这不是输入链路、CPS/UAPC、视频解码或回包外层包装问题。0.2.43 的点击与串流
证据保留在 `reports/gui-0.2.43-cps-1`。

## 正式修复

实现位置：

- `app/src/mihoyo/combo_login_data.hpp::ResolveLegacyGenshinAccountType`
- `app/src/mihoyo/sdk_bridge.cpp` 的 `login_login`
- `app/src/mihoyo/login_store.cpp` 的 `sdk_login_data` 向后兼容持久化
- `app/src/mihoyo/qr_login.cpp` 的 QR → SDK 元数据提取

恢复条件全部满足时才补 `1`，且绝不覆盖已有值：

1. 解码后的 SDK 数据是对象；
2. 不含 `account_type`；
3. `app_id == "4"`（原神国服）；
4. `channel_id == "1"`（官方渠道）；
5. `open_id == account_id`；
6. `account_id` 是合法、非零、无前导零、不超过 int64 的十进制数字。

不满足任一条就保持原样，不把类型 1 外推到 hkrpg/nap，也不修改存档中的账号
信息。新扫码/网页登录返回的官方元数据（`combo_id`、`account_type`、
`heartbeat`、`asterisk_name`、展开后的 `data`）会随加密 vault 保存并在
`login_login` 中回传。保留字段 `device_id/open_id/combo_token/channel_token/
app_id/channel_id` 不允许由嵌套数据覆盖。

`login_login` 中 `app_id/channel_id` 以 JSON 数字输出；`channel_token` 仅在
非空时加入；`login_get_asterisk_name` 返回保存的官方昵称。
