# 终末地 DTLS/SCTP 大包接收修复（2026-10-26）

## 可重复验证的缺陷

`peer_connection.c` 的加密 UDP 缓冲已是 2048 字节，但解密目标仍为
`temp_buf[CONFIG_MTU]`，即 1300 字节。Mbed TLS 的 `ssl_read` 对过小目标
并不报错，而是先返回前缀、保留尾部。应用把两次结果分别交给 SCTP，
破坏原包边界与整包校验，导致某些可靠流的首片永远无法重组。

修改仅让明文接收缓冲与现有加密数据报缓冲同为
`CONFIG_DATAGRAM_BUFFER_SIZE`（2048）。发送 MTU 1300、SCTP MTU 1200、
队列容量、TLS 校验和手柄线格式均未改变。这是有复现证据的必要依赖补丁，
不是整体升级或任意改动第三方库。

## 修复前的模拟器证据

隔离报告 `outputs/endfield-title-20261026/fragment-state/status.json`：

- 约 50 秒：接收重组 1092 字节、流内待交付 8 项，业务消息 28。
- 约 100 秒：接收重组仍 1092 字节、待交付增至 48 项，业务消息仍 28。
- 两次流 1 队首均 FIRST=0、LAST=1，缺首片但尾片已到。
- 本地发送字节、未确认项、重传项均为 0，接收失败标志为 0；底层 DTLS
  读计数仍增长。因此“本地发送成功”不能证明 SDK 消息持续可达。

这些 GDB 采样只读取计数、标志和相对差值，不读取包体、账号或地址。
此前视频持续播放但业务停滞的轮次不能据此认定为手柄映射问题。

## 主机验证

- `peer_dtls_loop` 新增 1460 字节明文包测试：旧实现确定失败，修改后一次
  完整交给 SCTP，且发送 MTU 保持 1300。
- `dtls_handshake` 使用真实 Mbed TLS、内存数据报和随机本地证书：确认旧
  1300 目标返回 1300+160；2048 目标完整返回 1460。测试服务端临时使用
  较大 MTU 以构造来包，不影响生产配置；同时保留错误指纹拒绝与首个握手包
  丢失重传测试。
- 完整构建 6 个 DTLS/UDP 主机目标后，6 项 ctest 全通过。
- 安全日志监测测试通过。无测试使用真实账号或保存凭据。

## 本轮 APK 对照

继续核对用户提供 APK 的既有本地反编译，而非假设 Android Java 层已包含
全部传输实现。`pcgwqv/pcgcoq.java` 的 `pcgcrk` 按递增 index 保存 GameData，
`BusinessDataConfirm` 解析 index 后由 `pcgmyu` 移除待确认项；
`GameDataChannelProtocol` 和其代理保留 keyed/unkeyed 两种收发入口。
这属于应用确认层，与下层 DTLS 保持完整 SCTP 包边界是两件事。仅补 SDK
回包或增加应用层重试，不会修复本次确定重现的下层截断问题。

未照搬 APK 将 key 或原始业务数据写日志的行为，未添加账户/付费/同意协议
的自动操作，也不把上述局部核对称为 APK 已完整复刻。
