# 0.2.86：接收恢复移植候选

## 本版范围

将 APK 调查中已证实的恢复架构用于当前原生 WeLink 串流：独立补包时钟、
每个缺口单独计时/重试、按需包缓冲、受限恢复和诊断；配合 Switch 侧调度与
码率上限控制。**不是整个 Android 内核完全移植，也不是“已证明实机不卡”。**

保持 H5/WeLink 已工作的登录、派发和输入协议，不把 Android SDK 身份混进 H5
会话；不改 TLS/DTLS 校验，不输出凭据，不把 Android .so 装进 NRO。

## 收包与恢复

- 新 `extern/libpeer/src/rtp_recovery.c` 从原来的 depacketizer 中分离恢复职责。
  即使已知缺口后暂时没有新 RTP 到达，peer owner 的正常空闲轮询也会驱动补包。
  如果最后一个包丢失、此后没有任何更高序号，单靠 NACK 仍无法知道其存在；
  原有停流/关键帧请求保护保留。
- 缺口各自保存发现时间、上次请求和次数。终末地初次等待 16 ms，最多 5 次；
  重试采用 ICE 已缓存 RTT 提示，夹在 10 ms 与当前修复预算的 1/3 之间，
  没有 RTT 时用 25 ms。这个间隔是 Switch 的预算适配，**不是 APK 的 100 ms
  常量原样复制，也不是实现了完整 GCC**。
- 每 5 ms 最多发 2 个 NACK 数据报，每个带 PID/BLP；成功发送后才增加尝试数。
  加密错误、socket 错误、短写不被记为发送成功；失败也受发送频率约束。
- NACK 定时器只读取 owner-local ICE RTT，不在高频收包路径调用需要 SCTP
  全局锁的 getsockopt。公开的慢速 RTT 诊断接口仍保留。
- 终末地包窗口从 512 槽起，按需翻倍至 Switch 默认上限 2048；内部实现允许
  显式配置的 8192 上限，但本版终末地不启用。正常顺序帧立即交付，没有固定
  增加 120 ms 播放延迟。120 ms 是缺口修复机会的预算，不是帧缓冲目标。
- 原神及其他未选择新窗口配置的 peer 保持默认固定 128 槽、原有 30 ms 预算；
  也获得独立、逐缺口的有界补包。未启用新窗口的 peer 保持立即首次 NACK、
  10 ms 重试间隔，而不是给所有游戏强制套用终末地参数。
- 扩容先成功取得全部新内存，再迁移、释放旧内存；失败保留原窗口。失败后
  一秒内不因每个新包反复申请，避免内存不足时的分配风暴。
- 大序号前跳采用一次有界元数据扫描，不能按远端给出的任意跳号做无界循环。
  修复后的连续包每次最多处理 64 个，后续 owner 轮询继续交付；超时清理也
  使用共享 64 步工作预算，不能因为窗口扩容就一次灌出数百个视频单元。
- 缺口时间使用单调时钟，覆盖 32 位绕回。保留旧缺口不能提前淘汰新缺口的
  0.2.85 修复和单次 2 ms 排空宽限。期限实际执行仍依赖 owner 得到调度，
  不能把 120 ms 配置值说成任何线程停顿下都能达到的端到端时限。
- 未知损坏、参考链损坏仍请求 IDR；不放行损坏 AU、不输出已知损坏画面。
  未证明可安全丢弃的非参考帧，不据字符串或猜测改变恢复门禁。

默认终末地修复包存储约 0.8 MB 起，最多约 3.2 MB，加少量元数据；扩容时旧、
新分配短暂共存。这里不是解码队列，不改变原有有界解码/显示队列。更大窗口
并不能修复超过期限的断网，也不能保证避免所有本机调度拥塞。

## 调度与会话内码率上限

WeLink owner 采用“有界收包 → 信令 → 有界收包 → 会话任务”，每次收包仍是
最多 64 次 peer poll 或 2 ms。没有新增第二个 peer owner。它减少控制工作前后
积压的机会，**不能抢占某一次已经阻塞的信令调用**；因此不能据此宣称消除
旧日志中的 350 ms 历史峰值。

新增 `endfield/adaptive_bitrate.hpp`：通过已有、验证过的
`ResetVideoBitrate` + `autoBitrateAdjust` 范围命令控制会话上限。

- 只用真实传输层损坏、修复超时和窗口淘汰观察压力，不采用 UI/显示跳帧或
  打开悬浮窗的次数来推断网络丢包。
- 两个连续约 5 秒压力窗口才降上限至当前 75%；不低于用户所选档位的 floor。
  至少约 30 秒正常交付后缓慢恢复，每次约 10%、至少 250 kbps，不超过用户
  所选档位的原始 ceiling。变化有冷却，空流量和长观察间隔不算稳定交付。
- 手动选择档位优先并重置控制器；自动调整不写入保存的用户档位或改变帧率。
  已保存 60 FPS 的用户仍保持 60，不强制改回 30。
- 成功只表示本地控制通道接受，不代表服务器已实际改变编码。失败不更新
  本地已发送上限，后续观察仍有冷却。面板显示“自适应上限请求”，不冒充
  实测码率；实测值仍看视频 payload Mbps。
- floor/ceiling 写入顺序和校验共享原有 helper；不加入猜测的命令。

这是 Switch 接收损坏驱动的保守闭环，不是从 APK 完整还原的带宽估计器。

## 新增中文诊断

保持每 5 秒快照以及原有受管历史日志轮换，不增加逐包 SD 日志。新增：

| 事件 | 用途 |
| --- | --- |
| `VIDEO_RTP_NACK_PACKETS / NACK_RETRIES` | 请求涉及包数、再次请求包数，不是丢包率 |
| `VIDEO_RTP_NACK_RECOVERED` | 请求后填回缺口的包数；不能证明一定是重传而非迟到原包 |
| `VIDEO_RTP_NACK_EXHAUSTED` | 达五次请求上限的缺口数 |
| `VIDEO_RTP_NACK_SEND_FAILURES` | 本地保护/发送失败，不是服务器拒绝 |
| `VIDEO_RTP_REPAIR_MAX_MS` | 缺口发现至填回的会话最大时间，不是网络 RTT |
| `VIDEO_RTP_TIMEOUT_SKIPS / CAPACITY_SKIPS` | 区分时间不足和槽位不足；后者按跳过的序号统计，不直接当网络丢包数 |
| `VIDEO_RTP_WINDOW_CAPACITY / WINDOW_PEAK` | 实际分配槽数、暂存包峰值 |
| `VIDEO_RTP_WINDOW_GROWTHS / WINDOW_ALLOC_FAILURES` | 扩容及分配失败 |
| `ENDFIELD_ADAPTIVE_BITRATE_SENT / SEND_FAILED / CEILING` | 控制请求结果与本地上限，均非远端 ACK 或实测 Mbps |

英文事件与中文含义都保留。自动安全日志仍会在游戏运行时记录，无须一直开面板。

## 验证与未完成项

- 最终 13 项生产 CTest 全通过：DTLS、peer 空闲循环、RTCP 接收/发送、NACK、
  Receiver Report、UDP poll、本机地址、H.264 组帧、重排、新恢复、内存分配失败。
- 23 项应用侧主机回归通过，涉及自适应码率、设置范围、收包调度、语言、账号
  策略、WeLink 协议/桥、输入、原神 launch flow、共享解码队列/恢复与显示时钟。
- peer 空闲循环、RTCP、RTP 重排、新恢复、分配失败 5 项各重复 20 次通过。
- 确定性模拟：1024 个 RTP 包，包含连续丢失、20 ms 补包延迟、序号绕回，
  交付 1024，填回 96 个已请求缺口，超时/容量淘汰 0。数据是模拟 RTP/NAL，
  不是真实 H.264 解码、实际游戏画面或真实网络吞吐证明。
- 完整 devkitA64 NRO 构建和最终增量重编译、版本检查通过。最终相关目标文件
  的时间晚于最后生产源码修改。保留对应 ELF 供后续崩溃定位。
- 本轮没有新的 yuzu/在线会话/实机持续运行验收，不能承诺恒定 60 FPS、零卡顿
  或声音问题全部解决。没有自动向 Switch 写入版本。

尚未完成：APK 的 `wlfec-01` 冗余布局与实际会话协商、完整 REMB/TWCC/GCC，
以及实机弱网下的长时间验收。本版**没有宣称或假广告这些功能**；不能只往 SDP
写名称就打开，也没有把 Moonlight 的不同服务器协议混进 WeLink。
