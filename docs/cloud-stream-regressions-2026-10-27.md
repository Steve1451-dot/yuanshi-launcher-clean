# 0.2.79：原神身份回归与 Moonlight 风格分阶段诊断

## 两份实机日志不是同一类故障

用户目录“新建文件夹 (2)”：0.2.78 终末地，最低码率 + 60 FPS、手持 Joy-Con。
86→91 秒仍解出 299 帧，141→161 秒却只解出 3 帧。最终 5,804 完整 AU，
3,726 解码帧，2,078 客户端丢弃，其中 2,077 是等待关键帧；解码错误与队列
拥塞事件均为 0。累计平均解码 11.79 ms、最大 35.59 ms，排队均值 5.36 ms。
收包循环最大间隔曾为 278 ms，后到 617 ms，过晚包上升至 3,237。
这些证据不支持直接认定“硬解慢”或“只有 Wi-Fi 差”；本机调度/阻塞和外部网络
尚需区分，网络受损后关键帧恢复是停画面的直接症状。音频输出计数增长但仍有
1,331 丢弃、164 次断粮，不代表已通过人耳确认。此轮记录了主动退出与清理。

用户随后目录“新建文件夹”：0.2.78 原神，保存登录与派发成功，但约 20 秒 DTLS
返回 -9984（证书校验失败）；视频/音频/渲染全为 0，28 秒仍有导出日志操作。
未提供同次 fatal dump，不能据此把连接失败称为已确认的进程崩溃。

登录 key/vault 未读取明文；仅为隔离运行复制用户授权的加密登录对，不进公开包。

## 可复现的原神回归

原神为 SDP answerer。peer_connection_set_remote_description 先解析服务器指纹，
紧接着 peer_connection_create_answer → create_sdp 却把 remote_fingerprint 清空。
终末地为 offerer，后收远端 answer，故同一缺陷不按相同顺序触发。

新增 peer_dtls_setup_test：收到含正确指纹的 offer → 生成本地 answer → 指纹仍在。
修改前实测失败“creating local answer erased ... remote offer fingerprint”；修改后通过。
修复将清理旧身份移到替换远端描述时；新本地 offer 也清空旧身份，本地 answer
则保留刚解析的远端身份。另测新描述缺少指纹不能继承旧值。
真实 DTLS 测试仍拒绝错误指纹，没有关闭证书校验、放宽 TLS/SRTP 或忽略日期。
新增安全标量 RTC_DTLS_REMOTE_PIN_PRESENT；不打印指纹内容。
证书错误以专门中文状态显示，不再只有“连接丢失”。

原神失败/游戏结束路径原来直接从网络线程调用 show_diagnostics，触碰 Borealis
可见性和焦点。现在只结束工作；UI 的 draw 观察 finished_ 后打开面板，避免
失败时引入跨线程界面操作。这是确定的不安全代码路径，不据此宣称已复现所有
用户所说的崩溃。

## Moonlight 参考与借鉴范围

核查 XITRIX/Moonlight-Switch 提交 a75fee223914f36ec26b29739d95331307960fa3：

- app/src/streaming_view.cpp 区分接收、解码、渲染帧率以及各阶段时延。
- MoonlightSession.cpp 约每 250 ms 更新统计，不把所有开局累计值当当前性能。
- FFmpegVideoDecoder.cpp 的线程策略与本项目旧 frame-thread 策略不同，不能
  未经实机验证就盲目切成 slice-thread：单 slice 云流可能反而失去吞吐。
- AudrenAudioRenderer.cpp 使用 audren + 软件 Opus，而本项目为 hwopus + audout；
  不是调低 PCM 音质就能直接节省已接收网络流量，也未凭空声称换后端必定解决无声。

来源：
https://github.com/XITRIX/Moonlight-Switch/tree/a75fee223914f36ec26b29739d95331307960fa3
https://www.rfc-editor.org/rfc/rfc5763.html

没有搬 Moonlight/Sunshine 网络协议去替换米哈游/WeLink 鉴权、信令和媒体协议。
HUD 和计数适配代码为本项目实现，沿用仓库现有授权，不整段移植外部 UI。

## 新悬浮窗与减少本地干扰

仍通过触屏悬浮球 → 性能悬浮窗开启，不修改手柄映射/打开手势/已保存帧率。
两条游戏流使用同一面板，最近约 1 秒区间显示：完整 AU 接收 FPS、解码 FPS、
新帧提交 FPS，解码/排队/渲染 CPU 提交耗时，等待关键帧与拥塞丢弃，本地显示
跳帧，音频已播放时长/断粮/丢弃，以及整次会话最大轮询间隔。

新帧提交不计重复绘制旧帧，不是物理屏幕刷新或 GPU 完成的证明。渲染耗时是
CPU 提交耗时，最大轮询间隔明确为整次会话；网络 RTT、真实空口丢包率和服务器
编码耗时不可获得时不捏造。

UI 操作区间内的显示跳帧另计 VIDEO_UI_INTERVAL_PRESENT_SKIPS，其余区间为
VIDEO_GAMEPLAY_PRESENT_SKIPS。是时间关联分类，不是断言全部由 UI 引起；真实
网络/恢复丢弃仍照实保留，绝不为了数字好看把 UI 期间的丢包抹掉。

安全日志自动保存上限从每 250 ms 合并到每 2 秒；首轮/退出仍会刷新，手动导出
不变。突然掉电可能丢失最后约 2 秒自动日志，这是减少 SD/CPU 争用的明确权衡。
普通原神游玩不再写 frame_thumb.log，只有显式 autotest 写测试缩略图。
不新增长度无界的队列或逐包/逐帧写卡，不修改 TLS 身份、Joy-Con 或画质档位。

## 真实运行中发现的进入路由不一致

第一次修复后的原神运行 176 秒：DTLS 成功，远端身份存在，4,280 帧解码、
0 解码错误/丢弃，但实际画面仍是门前“点击进入”；自动进入共发 10 次手柄 A。
手动“继续”原已按游戏使用 ContinueViaGamepad，自动/测试进入却直接检查
gamepad_transport。虚拟手柄强制开启后，原神标题页错误走了手柄路径。

两条自动进入路径改为复用相同策略：原神/绝区零标题走指针，崩铁保留手柄确认；
进入后的真实手柄编码与 Joy-Con 映射不变。随后同次 yuzu 日志只发送一次指针
进入，收到游戏进入 SDK 事件；解码器缩略图确认可见角色与游戏 HUD，不只是门。
该轮运行至 185 秒，4,370 帧、0 解码错误/丢弃，DTLS 返回 0、身份标量为 1。
音频提交/播放计数增长、输出错误 0，但有输出丢弃和缓冲耗尽计数，未声称人耳
或实机声音通过。总渲染次数包含旧帧重绘，不将其当独立帧率。

终末地同时进行了 64 秒兼容性冒烟：offerer 身份校验正常，1,838 帧，解码错误 0；
有 191 个客户端恢复/拥塞丢弃。主动停止以优先原神；不是终末地长时稳定证明。

## 排队查询的有界恢复

后续原神长测首轮在排队阶段出现 DISPATCH_NETWORK_ERROR，随后 QUEUE_LEFT 成功；
未到 DTLS/视频，原日志丢失了具体 CURLcode，不能据 40 秒间隔断言哪一层超时。
现保留数字 CURLcode/HTTP 状态，不输出异常文本、URL、票据或响应体。
仅已存在票据的只读 Poll 可对 DNS/连接/超时/空回复/收发错误再试两次，退避
0.5/1 秒、可取消，且仍受总排队截止时间限制。不会重放初始分配或 ACK；证书、
认证、API 拒绝、未知异常不重试。查询重试保留首页的排队状态。
合成测试覆盖成功恢复、三次总尝试后退队、证书错误不重试、取消清理以及不重放
初始分配，实际网络恢复与设备长测仍需单独记录。

新增独立、严格匹配的 600 秒 soak 和本地 UI probe 标记，仅配合原有 autotest
启用。UI probe 在进入窗口之后于 UI 线程开关设置六次、显示 HUD，不改变画质、
不发送游戏输入、不确认对话；实体输入/触摸会停止探测。默认测试仍为 170 秒，
正常运行无标记时完全不启用。公开包不附带这些标记或任何账号数据。
