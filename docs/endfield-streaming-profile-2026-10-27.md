## 找到并修正的硬解接入错误

实际随包 libavcodec.a 只有 ff_h264_decoder 与 ff_h264_nvtegra_hwaccel，
没有 h264_nvtegra 独立解码器。旧代码用 avcodec_find_decoder_by_name("h264_nvtegra")，
因此在找到硬件设备之前就失败，自动落回软件。这是可从符号和源代码交叉确认的缺陷。

正确接法是普通 H.264 解码器，通过 avcodec_get_hw_config 查找 NVTEGRA 的
HW_DEVICE_CTX 配置，创建对应设备，用 get_format 选择硬件表面。补上帧率及
90 kHz RTP 时间基；NVTEGRA 的动态时钟配置会读取帧率，不能留 0/1。
依据：

- https://github.com/FFmpeg/FFmpeg/blob/master/doc/examples/hw_decode.c
- https://ffmpeg.org/pipermail/ffmpeg-devel/2024-May/328557.html

只有初始化成功不等于已经解出硬件帧。新增初始化阶段/原始错误码、实际硬解帧数，
拒绝把软件帧标作硬解。设备创建后首次解码仍可能不兼容：仅当从未向 UI/GPU 发布
任何帧时，允许一次软件重建并请求新 IDR；有已发布帧时不在后台释放 UI 持有的表面。
软件备选仍是 3 个解码线程，视频队列保持原有长度与时间上限。

两条云客户端的 CPU 亮度采样都加了格式检查，不能把 block-linear NVTEGRA 表面
当成线性亮度平面。正常硬解显示保持 Deko3D 既有零拷贝路径，不新增逐帧 CPU 下载。

## 有针对性的优化与下一次判读

终末地音频抗抖目标从 40→60 ms：启动/重排/输出队列仍有固定上限；会增加少量
音频缓冲延迟，并不是降低网络码率。保留 0.2.77 的输出不断流修复。

新增固定标签的聚合统计，按原快照周期输出，不逐包/逐帧写卡：

| 指标 | 用于区分 |
| --- | --- |
| 硬解阶段、返回码、实际硬解帧数 | 真正启用还是初始化/首帧失败回退 |
| 平均/最大解码耗时、排队耗时、拥塞清理数 | 解码是否真的超过每帧预算 |
| 等待关键帧丢弃、外部 resync、重排/过晚/超时 | 丢帧后恢复等待是否放大卡顿 |
| 轮询平均/最大间隔 | 本机网络线程是否被调度/本地工作长时间阻塞 |
| 显示队列旧帧跳过、视频有效字节数 | 显示跟不上与到达画面本身减少 |

没有直接把某一热点/网卡归咎为根因；当前日志不足以分开无线链路、移动网络、
服务端路径和本地收包调度。也未修改系统超频配置、电压、TLS/SRTP 校验或重放保护。
建议先用默认系统频率取得修复后的实机数据，再考虑是否值得受控对比频率。
sys-clk 自身也按手持/充电/底座施加不同限制，不应在未知机型、电源和温度条件下
照抄频率或解除限制：https://github.com/retronx-team/sys-clk 。实验 NVDEC 使用后端
自带的正常动态频率请求，并未更改用户的系统超频配置或电压。

### 隔离 yuzu 的前两轮（均为 300 秒期限）

第一轮：实际 NVTEGRA 格式硬解 15,806 帧，硬解回退/解码错误/解码拥塞次数
均为 0，等待关键帧丢弃 8，损坏 AU 4。设备播放 13,315,680 采样，音频输出
错误 0、丢弃 9、缓冲耗尽 22。此轮没有发进入游戏确认键，不能称作角色场景验证。

第二轮：初始化成功后，首帧返回 AVERROR_UNKNOWN (-1313558101)，一次安全
回退为软件；此后实际软解 14,814 帧、解码错误 0，解码拥塞事件 3、等待关键帧
丢弃 406、损坏 AU 21。仅在检查真实标题画面后允许一次手柄确认，实际解码截图
已看到角色场景。设备播放 13,414,080 采样、输出错误 0，但还有音频缓冲耗尽
203 次。两轮均由测试期限结束并执行清理，不是自发崩溃。

因此“已接通硬解”和“每次开局都稳定使用硬解”是不同结论；第二轮的首帧兼容
问题不能隐去。两轮不是相同场景/节点的受控 A/B，也不能用各自丢帧数直接计算
优化百分比。硬解调用平均耗时 248 微秒、软解 8,221 微秒仅是 yuzu 中提交/接收
调用的墙钟统计，不是物理 NVDEC 的独立硬件耗时或端到端延迟；最大调用分别达到
360,706 / 201,292 微秒，平均值不能掩盖长尾。

显式 autotest 才允许有界、低频硬件帧下载截图；正常播放不作此下载。测试截图
会扰动 UI 性能，因此不把截图开启时的显示队列跳帧当成无诊断开销的显示性能。

### 后续发现与交付边界（不能略去）

第三轮 180 秒：NVTEGRA 返回 8,617 帧、解码错误 0，但硬件帧下载截图持续为黑。
第四轮以非 256 字节 pitch 强制后端 CPU 下载，排除只依赖 VIC 下载的情况，
164 秒后主动停止：仅 145 硬件格式输出帧、144 次 AVERROR_UNKNOWN，截图仍黑。
低频 CPU 下载仍走 FFmpeg 的 transfer API，没有将 GPU 映射误当线性亮度。
这否定了“硬解帧计数增长就能证明画面正确”的验收捷径。

尝试在隔离 yuzu 配置将 NVDEC 模拟后端改为 CPU 做独立对照，但在 5 秒的游戏
授权阶段返回 -1056，未到媒体阶段。没有绕过授权，也没有继续无界重试。
故不能声称已确定是模拟器 GPU 后端的问题，更不能声称实机硬解画面已通过。

最终同一个 NRO 默认保留可用的软解路径；修正后的硬解代码仅显式实验启用。
在 AppHomePath 下的 cloudgenshin-nvdec-probe.txt 写入一行 CGNX_NVDEC_PROBE_V1
（LF 或 CRLF），下次会话才尝试硬解。缺失、无效、超长文件均不启用；它不会
触发自动排队、自动按键或截图。移走此文件后重新进入会话即可恢复默认软解。
公开安装包不附此标记，也不附任何 autotest 标记、登录库或私有运行目录。

默认软解不再故意查找不存在的 h264_nvtegra，且用中文说明硬解尚待实机验收。
本版落地的是入口修正、首帧失败安全回退、音频 60 ms 抗抖和可判读的分段诊断，
不是已经完成物理 Switch 硬解优化或全部稳定性验收。

### 实机验收方法

保留用户保存的最低码率档 + 60 FPS、附着双 Joy-Con、现有登录库；先不超频。
至少持续运行 10–15 分钟，保留完整安全日志。重点检查：

- 默认软解应先查看解码耗时与拥塞；只有显式硬解实验才要求实际硬解帧增长、
  首次回退次数为 0，而且需要同时确认正确画面，不能只见初始化就绪。
- 60 FPS 的每帧预算约 16.7 ms；持续高解码耗时伴随拥塞才支持解码瓶颈。
- 轮询长间隔、RTP 损坏/过晚和等待 IDR 上升，要分开本地调度与外部网络问题。
- 音频已播放采样持续增长是输出服务进展，仍需人耳确认物理扬声器可听见。
- 断流与崩溃分开：若进程自发退出，需要同一次运行的 fatal/crash 信息；不能用
  用户退出或测试超时的清理日志推断崩溃。

尚未取得 0.2.78 物理 Switch 长测结果，不保证全部卡顿、声音和掉线已解决。
