# 0.2.81：原神与终末地的显示调度

## 本轮范围

按用户要求继续修调度，不启动 yuzu、不排队、不使用账号、不运行实机测试。
原神和终末地原生串流视图都接入本次显示调度。保留 0.2.80 的收包/补传恢复，
不修改登录、手柄编码、码率/帧率保存值、硬解选择或音频后端。

## 修复内容

### 按视频时间戳选择帧

两处原生视图原先未向 AVFrameHolder 提供目标时间戳。软件帧线程一次输出
多帧时，默认选择会一直丢到最新帧，未来才应显示的帧也可能替代当前帧。

新增 UI 线程持有的 NativePresentationClock，用单调时钟推进 90 kHz RTP
时间戳，沿用现有 DecideFrame 的 750 tick 提前容差。首帧立即锚定队头；
正常 30/60 FPS 序列无固定预缓冲等待。尚未到时的帧留在原有有界队列，
真正错过显示机会的旧帧仍丢弃。UI 暂停超过 250 ms、时间倒退或新视频帧与
时钟偏差超过 100 ms 时重新定位，避免积累无限回放延迟；源重置用 epoch
重新锚定，正常 RTP 绕回不触发重置。缺少 PTS 时回退原有最新帧策略。

队列容量不增加，也不插帧；这仍有平滑性和延迟的取舍：首次到来的是短时
积压时，最多保留现有 3 帧（30 FPS 下队头至队尾约 67 ms），不是无条件
只取最新帧。GFN 仍使用其外部音频派生目标时间戳，不改成这个视频时钟。
本次不实现原生音视频统一时钟，不能据此宣称音画同步已验收。

### 帧引用保护和重置

原 get 在队列锁外把原始指针借给 UI 回调；队列 cleanup 能释放该指针背后的
引用。新增 AVFrameReference，在锁内取得独立引用，锁外绘制。两个复用的
AVFrame 头允许引用失败时保留上一帧、下次重试；像素存储仅增加引用，不复制。
同一代帧反复刷新不重复分配 AVFrame 头。cleanup 不触碰 UI 持有的引用。

generation 不再随 cleanup 归零，以免新视频帧与渲染器缓存的旧编号混淆。
视图销毁后由 UI 释放引用，GPU fence / 映射 / 表面退出顺序不变，没有从网络
线程提前释放 GPU 正在使用的表面。现有网络线程 request_stop 路径保留。
这修复的是确定的所有权缺口，不证明用户过往全部崩溃都由这一处造成。

### 区分交给渲染器的帧和实际提交的帧

Deko3D 上传槽或命令 fence 忙时，可能继续画上一代帧。原来视图按显示队列的
reused 标志计数，可能把这一轮误认为新帧，也可能把下一轮成功重试算作重复。
现在渲染器报告实际提交的 generation，两处原生视图据此区分新帧与重复帧。
这仅为提交身份，不代表 GPU 完成、物理屏幕已显示或真实无线丢包。

现有每 5 秒安全快照增加：

- VIDEO_RENDER_DEFERRED_SUBMISSIONS：提交的帧不同于本轮提供的新帧。
- VIDEO_PRESENT_REFERENCE_FAILURES：显示帧引用失败。
- VIDEO_PRESENT_CLOCK_REBASES：时钟追到最新视频位置的次数。
- VIDEO_PRESENT_TIMING_HOLDS：等待未来时间戳、继续使用旧帧的次数。

均有中文解释并进入安全监测白名单；不逐帧写磁盘，不输出 PTS、地址或凭据。
正常 30 FPS 视频在 60 Hz UI 上重复显示不等于网络丢包，也不应算作异常卡顿。

## 验证边界

主机自动测试覆盖：30/60 FPS、连续 600 帧的双帧批次、时钟绕回、暂停追帧、
缺失 PTS、重置编号、引用失败重试、清理期间的回调与并发生产者，以及
渲染提交身份重试。旧版清理期间的回调用例实测断言失败，新版通过。
连续刷新 100 次不新增帧头分配；双帧批次 600 帧测试显示队列丢弃为 0，
这只是确定性输入场景，不是实机零丢帧结论。

Windows 队列/引用测试使用真实 FFmpeg 头与生产队列实现，但链接专门的
引用计数模型；不是实际 FFmpeg 解码、NVDEC 或 GPU fence 集成测试。
Linux 现有真实 FFmpeg 链接测试入口仍保留，本轮未在该环境执行。
主机 DTLS/UDP/RTP/H264 回归使用生产传输代码，不把引用模型当作网络测试。

本轮最终统一运行 23 项相关主机用例，全部通过；8 项 DTLS/UDP/RTP/H264
CTest 全部通过（包括错误证书拒绝）。完整 devkitA64 NRO 链接与内嵌版本校验
通过，构建配置 CLOUDGENSHIN_NATIVE=ON。冻结 ELF 确认包含生产 acquire/retain
实现；不是把主机策略测试当成 Switch 编译。
