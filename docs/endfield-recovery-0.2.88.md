# 0.2.88：终末地损坏恢复与共享补包调度修正

## 范围

在 0.2.87 上继续修终末地。保留该版本的原神即时损坏通知、60 ms 修复预算、
512→2048 包窗口和 250 ms 关键帧请求节奏。终末地保持 120 ms 修复预算、
512→2048 包窗口、原有会话自适应码率上限。没有更换登录身份或协议，未修改
保存的登录、手柄、语言、画质、帧率或解码器选择。

这不是全量 Android RTC 内核移植完成，也不是实机零卡顿验收。

## 终末地：不再因丢弃一个损坏 AU 清空此前完整画面

此前 `VlinkSession` 在交付完整 AU 前和每次 peer poll 后读取累计损坏计数。
计数变化会触发 `MediaPipeline::request_resync()`：清空此前完整的待解码帧、
推进 generation，并安排解码器重置。这比已知“损坏字节从未送入解码器”的
情况需要的操作更重。

现在接入生产 depacketizer 的 `onvideodamage`，在损坏 AU 被关闭的同一调用里
执行 `notify_video_damage()`。它保留此前完整 AU 和 generation，只拦住依赖
损坏参考链的后续非 IDR；完整 IDR 到达即可重新入队。去掉逐 peer poll 的
损坏计数查询和延迟通知，不会在随后一轮计时器中再清掉刚到的好 IDR。

没有放行损坏 AU，也没有删除真正解码失败、队列拥塞和显式 resync 的保护。
如果丢失最后一个包且后面完全没有新 RTP，仍可能需要原有停流 watchdog。

## 共享 RTP：没有到期请求时也限制扫描频率

0.2.86 的 NACK 扫描只在尝试发送后记录扫描时间。因此最初 16 ms 等待期间、
两次重试之间或一个缺口达到五次上限后，没有请求到期的完整窗口扫描可能
反复发生在高频 peer poll 中。窗口最大 2048 槽，弱网期间这种额外工作没有
补包收益。

现在空扫描也记录下一次机会：通常最多等 5 ms；若扫描已知下一次首发/重试
在 1～4 ms 后到期，则缩短到该期限。任何发送尝试后仍保留每 5 ms 最多两个
数据报的限制，包括本地发送失败。新到缺口在现有门限内可能等至多 5 ms
才被重新检查，实际时限还受 owner 调度影响。没有增加固定播放缓冲。

保留五次尝试上限、逐缺口年龄、单调时钟绕回处理、有界交付、分配失败退让，
以及“请求后填回不一定来自重传”的计数含义。这是减少无效 CPU 工作的修正，
不是实机 FPS 提升幅度的证明。

## 共享 PLI：加密失败不发送，短写不算成功

此前关键帧请求没有检查 SRTCP protect 返回值，protect 失败后仍尝试发送；
也把正数短写交给上层当作成功。新增失败注入测试复现后已修正：protect 失败
直接返回失败、不调用 socket；必须完整写入整个加密数据报才返回成功。

终末地关键帧成功/失败计数统一放到既有约 5 秒快照，不在持续恢复时每次请求
追加日志。成功仅表示本地完整发送，不是服务端 ACK 或已收到新关键帧。

## 两款游戏：分开记录恢复等待

新增有界、无分配的 `FrameRecoveryTimings`。状态变化复用现有队列锁，UI 和
日志只读取原子累计值，不增加 UI→队列锁依赖。首次启动不计入恢复过程。

| 事件 | 含义 |
| --- | --- |
| `VIDEO_RECOVERY_EPISODES / COMPLETED / SUPERSEDED` | 恢复过程、已有输出、被新损坏覆盖的过程次数 |
| `VIDEO_RECOVERY_PHASE` | 0 正常；1 等完整 IDR；2 IDR 已入队、等后续解码输出 |
| `VIDEO_RECOVERY_IDR_LAST_US / MAX_US` | 恢复开始到完整 IDR 入队的最近/最大微秒数 |
| `VIDEO_RECOVERY_OUTPUT_LAST_US / MAX_US` | IDR 入队到其后首批解码输出的最近/最大微秒数 |
| `VIDEO_RECOVERY_TOTAL_LAST_US / MAX_US` | 恢复开始到上述输出的最近/最大微秒数 |
| `ENDFIELD_KEYFRAME_REQUESTS / SEND_FAILURES` | 本地完整发送/失败次数，非远端确认 |

同一段等待 IDR 的多次损坏不会不断重置起点。每个恢复过程有独立 ticket：
旧的在途解码不能提前结束新的恢复；解码提交返回零帧也不能算恢复完成。
若已入队 IDR 尚未产生输出时又有新损坏，旧过程记为 superseded，新过程另计。
显式 resync、队列拥塞和解码失败也纳入同一恢复计时；启动等待不纳入。

这些值不是 RTT、纯解码 CPU 时间或屏幕冻结实测时长。第一段包含本地发现
损坏后的请求节奏、网络与服务端等待；第二段包含排队、解码和 codec 缓冲。
首批输出可能受解码器重排影响，不能据此证明某张恢复 IDR 已显示。原有显示
和解码阶段统计继续保留，所有值在中文安全日志中有释义。

## 重复测试额外发现：空闲停止可能丢失唤醒

本轮重复运行真实 `MediaPipeline` 主机测试时出现进程不退出。附加离线测试
进程读取线程栈，确认主线程卡在 `MediaPipeline::stop()` 的 `thread::join()`，
解码线程仍卡在 `decode_loop()` 的条件变量等待。

根因是停止路径虽然使用原子 `running_`，却在队列锁外更新谓词并通知；通知
可能落在解码线程检查谓词和进入等待之间，原子变量本身不能防止丢失通知。
修正为在同一个队列锁内将 `running_` 设为 false，再通知等待者。没有持锁
join、没有第二个 decoder owner，也没有改变真正解码任务的锁范围。

媒体管线测试增加 1000 次“无首包立即停止 / 刚解码完停止 / 重复请求停止”
循环，并加入 30 秒测试进程自终止保护，避免以后把死锁当成长时间测试运行。
该问题在主机真实线程模型中已复现；不能据此断言用户此前所有实机崩溃都是
同一原因，异常退出仍需对应崩溃地址和会话日志。

## 尚未完成

没有加入未经协商的 `goog-remb`、TWCC 或 `wlfec-01` 广告。FEC 冗余布局、
实际会话协商和完整 GCC 仍需进一步证实与实现。没有把 Android `.so` 直接
打入 Switch；也未开展新的在线账号、yuzu、实机长时间或弱网验收。
